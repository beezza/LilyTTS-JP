# LilyTTS-JP 設計書 v0.3

> 前提の計算資源: **RTX 5070 Ti（16GB）× 1 ＋ RTX 3050（6GB）× 1**
> 用途: **個人利用のみ（重みは公開しない）**
> 主データ: **ノベルゲーム由来の音声 5,000〜10,000時間**（本文・話者・音声が対応済み。**読み（ルビ）の情報は無い**。成人向けの台詞は**フィルタ済み**）
> 話者: **ゼロショット**（参照音声）と**話者ごとの微調整**（話者LoRA）の両方に対応する
> 最終更新: 2026-11-22
> 関連: 評価セットの自動構築は [LILYBENCH.md](LILYBENCH.md)、一から学習する参考設計は [DESIGN_fullscale.md](DESIGN_fullscale.md)。

---

## 0. TL;DR

- **既存の強い公開TTSに上乗せする**方針は変えない。狙うのは「日本語の読みとアクセントで SOTA、総合品質はベースと同等以上」。
- ゲーム音声 5〜10k時間は**スタジオ収録・話者ラベル付き・表現豊か**で、個人規模としては非常に強いデータ。これを主データにする。表現力と音質でもベースを上回ることを狙う。
- 構成は2段:
  1. **Yomi**: テキストを PK 列（カナ＋アクセント記号）に変換する。日本語 LLM + LoRA で、テキストだけで学習する。**ゲーム音声から復元した読み**（数百万文）を正解の読みとして使う。
  2. **Lily**: **Qwen3-TTS-12Hz-1.7B-Base** を LoRA で微調整し、PK 列に忠実に読ませる。
- **評価セットは完全自動で構築・採点する**（[LILYBENCH.md](LILYBENCH.md)）。ルビ・規則・既存の人手ラベル・自然音声と辞書の一致から正解を作り、既存手法が間違える文を自動で選ぶ。
- GPU の使い分け: **5070 Ti は学習と前処理の重い処理**、**3050（6GB）は軽い前処理・評価・Yomi の推論**。2枚で一緒に学習はしない。

## 1. 計算資源

| | RTX 5070 Ti | RTX 3050 |
|---|---|---|
| VRAM | 16GB | **6GB** |
| BF16 実効性能（目安） | ~30 TFLOPS | ~6 TFLOPS |
| 役割 | Lily と Yomi の学習、ASR による一括確認、大きいモデルの推論 | 音素認識・F0 抽出・UTMOS・SIM・トークン化・Yomi の推論（4bit） |

**3050（6GB）での運用ルール**
- 評価用のモデルは**常駐させず、1つずつ順に読み込む**。Whisper-large-v3 は fp16 で約3GB、UTMOSv2・WavLM-SV・HuBERT-base はそれぞれ 1GB 未満。
- Yomi の推論は 1.7B を 4bit 量子化（約1.2GB）するか、0.6B に蒸留したものを使う。
- Lily（1.7B）を 3050 で推論するのは難しい（bf16 で重みだけ約3.4GB、KV キャッシュを含めると余裕がない）。**Lily の推論と DPO 用のサンプル生成は 5070 Ti で行い**、学習の合間に回す。

## 2. 目標

| 指標 | 評価セット | 目標 |
|---|---|---|
| 読み正解率 ↑ | Yomi-Hard / Random | **比較した全モデル中1位**（Hard ≥ 95%、Random ≥ 99%） |
| アクセント句誤り率 ↓ | Accent | **比較した全モデル中1位**（≤ 8%） |
| CER ↓ | 公開ベンチの ja 部分 | ベースの 3.82 → **≤ 2.8** |
| カナCER ↓ | Basic | ベースの50%以下 |
| UTMOSv2 ↑ / SIM ↑ | Basic / Zero-shot | ベース以上（ゲーム音声で上積みを狙う） |
| 表現力 | Expressive（感情・叫び・ささやき） | ベースより指示追従・感情の一致率が高いこと |
| 初回音声の遅延 | 5070 Ti ローカル | ≤ 400ms |

比較対象: Qwen3-TTS（ベース）/ CosyVoice3 / Irodori-TTS / Sarashina2.2-TTS / Style-BERT-VITS2 JP-Extra / VoxCPM2。**個人利用なので、非商用ライセンスのモデルも比較対象として手元で動かせる。**

## 3. ベースモデル

- **第一候補: Qwen3-TTS-12Hz-1.7B-Base**（Apache-2.0、日本語 CER 3.82 の報告値、公式に微調整に対応）。12Hz で1秒あたりのフレーム数が少なく、学習が安い。
- 予備: Qwen3-TTS-12Hz-0.6B-Base（全パラメータ学習が可能）、Fun-CosyVoice3-0.5B。
- **P0 で LilyBench-JP を使って実測し、確定する**。

## 4. システム構成

```
入力テキスト（ルビ {今日|こんにち} / アクセント指定 {橋|ハ[シ} / スタイル指示 / 話者）
   │
   ▼
[正規化]（ルールは最小限）
   │
   ▼
[Yomi] 日本語LLM 〜1.7B + LoRA  → PK列  ^キョ]ーワ#ヨ]イ#テ]ンキデスネ$
   │   ルビ・アクセント指定の箇所は制約付きデコードで固定        （3050 で 4bit 推論）
   ▼
[Lily] Qwen3-TTS-12Hz-1.7B-Base + LoRA                            （5070 Ti）
   │   入力: 本文 <sep> PK ＋ 参照音声（または学習済みの話者ID） ＋ 任意のスタイル指示
   ▼
波形
```

- **PK の仕様**: ESPnet / pyopenjtalk の prosody 記号と互換。`^ $ ?`（文頭・文末・疑問）、`#`（句境界）、`[`（上昇）、`]`（核）、`_`（ポーズ）。カナと ASCII だけなので、語彙を追加しなくて済む。
- **Lily の入力のドロップアウト**: 「本文+PK」60% / 「PKのみ」25% / 「本文のみ」15%。

## 5. データ

### 5.1 構成（フィルタ後）

| データ | 時間 | 比率（学習時のサンプリング） | 役割 |
|---|---|---|---|
| **ノベルゲーム音声** | 5〜10k h（フィルタ後 4〜8k h 想定） | **~70%** | 主データ。音質・表現力・話者の多さ |
| ReazonSpeech（高品質部分） | ~1〜2k h | ~20% | 平坦な読み上げ口調、男性話者、ニュース的な語彙 |
| JSUT / JVS / JVNV / Common Voice ja | ~200h | ~10% | 標準的な読み上げ、アクセント教師（JSUT のラベル） |
| テキストのみ（青空文庫・Wikipedia・ゲームスクリプト・ニュース） | 数百万文 | — | Yomi の学習 |

**一般データを30%混ぜる理由**: ゲーム音声だけで学習すると、アニメ調の誇張した韻律や女性話者に偏り、**平叙文を普通に読む能力と男性の声が落ちる**ため。

### 5.2 ゲームデータの扱い

**利点**
- **音声そのものが読みの正解になる** → 声優は文脈を理解して読んでいるので、音声から読みを復元すれば、文脈付きの (本文, 読み) の組が数百万件できる（§5.4）。Yomi の学習と、評価の情報源 R4 に使う。
- **話者名** → 話者ラベルが最初から付いている（キャラクター単位）。
- **前後の台詞** → 文脈付きの学習が将来できる（v2 の候補。直前の台詞を条件にして韻律を決める）。
- 音声ファイルに BGM や効果音が入っていないので、音源分離が要らない。

**注意点と自動対策**

| 問題 | 対策 |
|---|---|
| スクリプトと実際の発話が違う（アドリブ・修正） | kotoba-whisper でカナCERを計算し、閾値を超えたら除外。部分的な違いは音素認識の結果で読みを修正する |
| 台詞の大半が記号や非言語（「っ……！」「はぁ、はぁ」、悲鳴など） | 文字種の比率で判定し、**非言語タグ**（`[息]` `[笑]` `[叫]` など）付きのデータに分ける。読み・アクセントの学習からは外す |
| 方言キャラ（関西弁など） | 話者単位で、推定アクセントと辞書のずれ、スクリプトの語彙を LLM で判定し、`<dialect:kansai>` などのタグを付ける。標準語のアクセント学習と評価からは除外する |
| 誇張された演技（叫び・泣き） | UTMOS や F0 の範囲で**スタイルタグ**を自動で付け、制御に使う。アクセント教師からは外す |
| 1作品・1キャラクターへの偏り | キャラクターごとのサンプリング上限（例: 1キャラ最大20h/epoch） |
| 音声と台詞の対応ずれ（抽出ミス） | ASR の一致確認（上記）で自動的に落ちる |

成人向けの台詞はフィルタ済みなので、追加の処理は不要。

**共通マニフェスト形式**: 既存のメタデータ（他の TTS と共用していたもの）を、`data_pipeline/novelgame/to_manifest.py` で次の JSONL に変換する。

```json
{"id": "2a046e12…aef8",
 "audio": "GalGame/sprite_Ao no Kanata no Four Rhythm/明日香/asuka_00956.ogg",
 "text": "安全教室ですか",
 "ruby": [{"start": 0, "end": 2, "reading": "アンゼン"}],
 "speaker": "sprite_Ao no Kanata no Four Rhythm/明日香",
 "title": "sprite_Ao no Kanata no Four Rhythm",
 "duration": 2.16, "duration_estimated": true,
 "src_status": "acoustic_and_asr_phone_match"}
```

| 元のフィールド | 扱い |
|---|---|
| `uid` | `id`（無ければ `catalog_id`、それも無ければ音声パスのハッシュ） |
| `audio_path` | `audio`（`--audio-root` からの相対パス。マウント先が変わっても使える） |
| `text` | `text`。インラインのルビ記法があれば取り除き、`ruby` に移す |
| `game_id` / `character_id` | `title` / `speaker`（`作品/キャラ`） |
| `performer_id` | 値があれば `voice_actor` |
| `duration_sec` / `duration_is_estimated` | `duration` / `duration_estimated`。`--probe-duration` で実際の長さに置き換える |
| `cleaning_status` | `src_status`、`text_check`、`phrase_end_mismatch`（§5.4 の表）。`--keep-status` で絞り込める |
| `original_transcript` | 本文と違えば `src_original_text`（人手修正前の台詞） |
| `split` | **使わない**。台詞単位の分割だと同じ作品が学習と評価の両方に入るので、作品単位で分け直す |
| `catalog_id` / `frames` ほか | 捨てる（他の TTS 用の情報） |

- ルビの読み取り元: ①`--ruby-text-field`（ルビ記法入りの本文があるフィールド）、②`--ruby-field` か自動検出（`ruby` / `rubies` / `furigana` / `ruby_spans` / `yomi`）、③`text` 内のインライン記法。記法は `｜漢字《かな》`、`漢字《かな》`、`{漢字|かな}`、`<ruby>`、`[ruby text=…]` に対応する。
- 読みはカタカナに統一する。傍点（`《・・》`）は捨てる。カナでない読みや位置のずれは警告に出す。
- `--report` で件数・時間・ステータス別件数・ルビの付与率・警告の種類・**元データに含まれるフィールド名の一覧**を出す。

### 5.3 前処理パイプラインと GPU 割り当て

| 段階 | GPU | 1万時間あたりの目安 |
|---|---|---|
| 長さ・音量の正規化、文字種判定、非言語タグ | CPU | — |
| ASR による一致確認（kotoba-whisper、バッチ処理） | **5070 Ti**（Lily の学習前にまとめて実行） | 2〜4日 |
| PK ラベラ（HuBERT-base の CTC 音素認識 + 辞書の N-best 照合 + F0 によるアクセント推定） | 3050 | 3〜5日 |
| UTMOSv2 とスタイルタグ | 3050 | 2〜3日 |
| Qwen3-TTS トークナイザによるトークン化 | 3050（遅ければ 5070 Ti） | 2〜4日 |

保存領域: ゲーム音声は OGG のままなら1万時間で約0.4〜0.5TB。処理後はトークンとメタデータだけ使うので、合計 1〜2TB の SSD で足りる。

### 5.4 PK ラベラ（音声から読みとアクセントを取る）

- **元データの `cleaning_status` で分かること**: 音素一致の判定は「元台詞を **OpenJTalk** で変換した音素」と「Whisper の書き起こしを正規化した音素」を比べたもの。Whisper が出すのも文字なので、どちらもテキストから推測した読みになり、**一致したことで分かるのは本文の語が正しいことだけで、漢字の読みは裏付けられていない**（G2P が同形異音語を読み違えると、両側で同じように読み違えるため）。したがって**読みは必ずこちらのラベラで音声から取る**。

  | `cleaning_status` | 本文の信頼度 | `text_check` | 認識器の教師 | アクセントの正解 |
  |---|---|---|---|---|
  | `human_original` / `human_corrected` | 最高（人が試聴） | `human` | ○ | ○ |
  | `ctc_confirms_original` | 高（別のCTCモデルが裏付け） | `ctc` | ○ | ○ |
  | `acoustic_and_asr_phone_match` | 高 | `asr_phone` | ○ | ○ |
  | `phrase_end_timing` | 高（句末の長音・促音だけ違う） | `asr_phone` + `phrase_end_mismatch` | ×（句末のラベルがずれる） | 句末を除けば ○ |

  `human_corrected` の元台詞（`original_transcript`）は `src_original_text` に残す。台本と実際の発話の違い（アドリブ）を分析するのに使える。
- **カナ音素認識器**: **reazon-research/japanese-wav2vec2-base-rs35kh**（約95M、ReazonSpeech 35k時間で文字 CTC を学習済み）の出力層をカナ語彙に付け替えて微調整する。日本語の音声認識をすでに学習しているので、少ない教師で早く収束する見込み。**評価の採点用には別系統のモデル**（rinna/japanese-hubert-base をカナ CTC に微調整したもの）を使い、学習の報酬と評価で同じモデルを使わないようにする。音声と完全に一致したカナの教師が必要だが、上の通りゲームデータの読みは保証されていないので、**段階的に作る**:
  1. 初期の教師: JSUT / JVS の人手の読み ＋ **辞書上の読みが一意な語だけでできた台詞**（同形異音語・数詞・未知語を含まない。この場合は G2P の読みがほぼ確実に正しい）。`phrase_end_mismatch` の台詞は除く。
  2. その認識器で、残りの台詞の読みを §5.4 の候補選択で復元する。
  3. 信頼度の高いものを教師に加えて再学習する（自己学習を2〜3回）。
- **OpenJTalk の読み誤りを自動で集める**: 元データの音素は OpenJTalk の読みなので、**音声から復元した読みが OpenJTalk の読みと食い違う台詞は、そのまま「OpenJTalk が読み違えた実例」になる**。食い違いの箇所を語ごとに集計すれば、どんな語で辞書が誤るかの一覧ができる。これは Yomi の重点学習データと、LilyBench-JP Yomi-Hard の情報源 R4 に使う（評価用の作品のものは評価だけに回す）。
- **読みの決定**: 本文から読み候補を作り（pyopenjtalk / UniDic / marine の N-best に、同形異音語辞書の全候補と助数詞の音便形を加える）、認識器のスコアで選ぶ。候補に正解が無いとき（当て字・キャラ名など）は認識器の出力を採用し、「固有読み」の印を付ける。
- **選別の偏りは小さい**: 元データの選別は語の一致を見ているだけなので、難しい読みの台詞が選択的に落とされているわけではない。落ちているのは主に、Whisper が別の表記で書いた台詞（珍しい固有名詞やキャラ名、早口、アドリブ）と考えられる。読みの難例は、採用済みの台詞の中に十分残っている。
- **アクセント**: 強制アライメント → RMVPE で F0 → 分類器。教師は JSUT の人手ラベル（評価用の部分は除外）。
- **信頼度**が低い発話は「本文のみ」入力の学習に回す。

## 6. 学習

### 6.1 Yomi（テキスト → PK）

- ベース候補: LLM-jp-3 1.8B / Sarashina2.2-1B / Qwen3-1.7B。テキストだけで安いので、3つとも試して選ぶ。
- データ: ①音声由来の (本文, PK)（ゲーム + ReazonSpeech で数百万文）、②青空文庫のルビと NHK NEWS WEB EASY のふりがな、③規則・辞書による難例の合成。**評価用の作品は除外する**。
- LoRA を 5070 Ti で約1〜2日学習し、その後 PK の正解一致を報酬にした GRPO を約1日。最後に 0.6B へ蒸留して 3050 用にする（任意）。

### 6.2 Lily（PK → 音声）

| 項目 | 設定 |
|---|---|
| ベース | Qwen3-TTS-12Hz-1.7B-Base |
| 方式 | LoRA（r=128、attention と MLP）。コーデックは凍結 |
| 話者 | **参照音声のみ**（話者IDの埋め込みは使わない）。同じ話者の別の台詞を参照音声にして学習する。話者を固定したいときは §6.4 の話者LoRA を使う |
| メモリ | bf16、gradient checkpointing、トークン数によるバッチ構成、8bit AdamW（sm_120 対応を確認） |
| データ量 | 7k h × 12.5Hz ≈ 3.2億フレーム/epoch |
| 計算量 | 2 epoch で約 4.3e18 FLOPs → **5070 Ti で約2〜4日**（MTP ヘッドの分を含む） |

### 6.3 選好学習（DPO）

- Lily で 5,000プロンプト × 4サンプルを生成する（5070 Ti で約半日）。
- 自動で採点する（3050）: 読み（音素認識器）・アクセント（推定器）・SIM・UTMOSv2。
- DPO-LoRA を数時間。**報酬に使うモデルと評価に使うモデルは別にする**（[LILYBENCH.md](LILYBENCH.md) §4）。

### 6.4 ゼロショットと話者ごとの微調整

本体（Lily）は**ゼロショット用の汎用モデル**として学習し、特定の声は**後から話者LoRAを足す**。本体を作り直さずに、話者を何人でも追加できる。

**ゼロショット（本体の学習時）**
- 参照音声は、**同じ話者の別の台詞**から 3〜10秒をランダムに選ぶ。同じ台詞を参照にすると、内容のコピーを覚えてしまうため。
- 参照音声の書き起こしも、本文と同じく「本文+PK」の形で与える。
- **学習に使わない話者**（タイトル単位で 50〜100話者）をゼロショット評価用に確保する。

**話者LoRA（話者ごとの微調整）**

| 項目 | 設定 |
|---|---|
| 土台 | 本体の LoRA を重みにマージしたモデル |
| 学習対象 | 新しい LoRA（r=16、attention のみ） |
| データ量 | 最小 10分、推奨 30分〜2時間（その話者の台詞のみ） |
| 学習量 | 1〜3k ステップ、学習率は低め（1e-4 程度） |
| 所要時間 | **5070 Ti で 15〜60分** |
| 保存サイズ | 1話者あたり数十MB |
| 推論 | 話者LoRA を切り替えて使う。参照音声も併用でき、感情やスタイルは参照音声で変える |

- **読みとアクセントは崩れにくい**: 読みは Yomi が決め、Lily は PK に従うだけなので、話者LoRA は「声とその話者らしい韻律」だけを学べばよい。念のため、微調整後に Yomi-Hard と Accent を自動で再評価し、ベースより悪化したら学習ステップを減らす（早期終了）。
- 過学習の対策: データの10%を一般データ（他の話者の PK 付き文）にし、PK への忠実さを保つ。

**話者適応の評価（LilyBench-JP Speaker-FT）**
- 学習に使っていない話者から 20話者を選び、10分 / 30分 / 2時間のデータで話者LoRA を作る。
- SIM、CER、UTMOSv2 をゼロショットと比べ、**どのくらいのデータ量で微調整がゼロショットを上回るか**を確かめる。
- 読み・アクセントがゼロショットから悪化しないこと（Δ ≤ +0.5pt）も確認する。

## 7. 評価（自動構築）: 要点

詳しくは [LILYBENCH.md](LILYBENCH.md)。

- **Yomi-Hard**: 正解の読みは4系統の独立した情報源から取る。①ルビ（青空文庫・NHK EASY）、②規則（数詞・助数詞・日付・単位）、③読み付き辞書（Wikipedia の読み・郵便番号データ・駅名）、④自然音声と辞書の照合。既存手法が誤る文を自動で選び、選別しないランダムなセットも同時に作る。
- **Accent**: ①JSUT の人手修正済みラベル、②辞書の予測と自然音声からの推定が一致したアクセント句。
- **採点**: 読みは「認識結果の照合」と「候補ごとの尤度比較」の2方式が一致したときだけ判定する。アクセントは F0 による推定器と、PASQA 型の誤り検出器（Lily でわざと誤ったアクセントの音声を作って学習する）で測る。
- **ベンチ自体の誤り**も、情報源どうしの一致率から自動で推定し、信頼区間として報告する。
- 漏洩防止のため、ゲームはタイトル単位、青空文庫は作品単位で、学習用と評価用に分ける。

## 11. 個人利用での注意（短く）

- 重みを公開しない個人利用でも、**生成した音声を公開するとき**は、特定の声優の声に似せた音声には肖像権・パブリシティや、ゲームの利用規約の問題が出うる。**生成音声は手元で使う**前提にする。
- ゲームの利用規約にデータ抽出の禁止条項がある作品もある。各自で判断する。
- 生成音声を外に出す可能性があるなら、透かし（AudioSeal 等）を入れておく。

## 12. リスク

| リスク | 対策 |
|---|---|
| ゲーム音声の韻律に偏る | 一般データを約30%混ぜる。スタイルタグで「平叙」を指定できるようにする。A4 で比率を検証 |
| LoRA では PK に十分従わない | rank を上げる → 0.6B を全パラメータで学習する → CosyVoice3-0.5B の順で退避する |
| 自動評価のラベルノイズ | 複数の情報源の一致で採用し、ノイズ率を推定して報告する。任意で30分程度の抜き取り確認 |
| 3050 の 6GB 不足 | モデルを1つずつ順に読み込む。重い処理は 5070 Ti の空き時間に回す |
| 前処理に時間がかかりすぎる | 5070 Ti で学習していない時間帯に一括処理する |
