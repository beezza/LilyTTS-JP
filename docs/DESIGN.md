# LilyTTS-JP 設計書 v0.2（RTX 5070 Ti + RTX 3050 版）

> 前提の計算資源: **RTX 5070 Ti（16GB）× 1 ＋ RTX 3050（8GB 想定）× 1**
> 最終更新: 2026-11-22
> 一から学習するフルスケール設計は [DESIGN_fullscale.md](DESIGN_fullscale.md)（参考）に移した。PK の仕様と LilyBench-JP の考え方はそちらと共通。

---

## 0. TL;DR

- 一から学習するのは不可能なので、**既存の強い公開 TTS（Apache-2.0）に上乗せする**。
- 狙うのは「全指標で SOTA」ではなく、**日本語の「読み」と「アクセント」で明確に SOTA**、総合品質は上位勢と同等。既存モデルが最も弱く（VoxCPM2 は「漢字の読みは弱い」と明記）、しかも**少ない計算量で改善できる**部分に集中する。
- 構成は2段:
  1. **読み・アクセント推定器（Yomi）**: 日本語 LLM（〜1.7B）を LoRA で学習し、テキストを PK 列（カナ＋アクセント記号）に変換する。**テキストだけで学習できる**ので安い。
  2. **音響モデル（Lily）**: **Qwen3-TTS-12Hz-1.7B-Base** を LoRA で微調整し、PK 列に忠実に読ませる。
- RTX 3050 は学習に混ぜない（DDP は遅い方の GPU に律速される）。**データの前処理・評価・サンプル生成の専用ワーカー**として、5070 Ti の学習と並行して動かす。
- 必要な GPU 時間は**約3〜5週間分**。

## 1. 計算資源の現実

| | H100 SXM | RTX 5070 Ti | RTX 3050 |
|---|---|---|---|
| VRAM | 80GB | 16GB | 8GB |
| BF16 実効性能（目安） | ~400 TFLOPS | **~30 TFLOPS** | ~8 TFLOPS |
| H100 比 | 1 | **約1/13** | 約1/50 |

※ 実効値は MFU 30〜40% を仮定した概算。

- フルスケール版の 8k〜15k H100時間は、5070 Ti では**約10〜20年**かかる → 不可能。
- 10万時間の音声は 48kHz で約35TB あり、ダウンロードも保存も現実的でない。
- → **事前学習は既存モデルに任せ、日本語に特化した微調整と前処理の質で勝つ**。

## 2. 目標（現実的な SOTA の定義）

| 指標 | 評価セット | 目標 | ねらい |
|---|---|---|---|
| 読み正解率 ↑ | LilyBench-JP **Yomi-Hard** | **全公開モデル中1位**（目標 ≥ 95%） | 主戦場 |
| アクセント句誤り率 ↓ | LilyBench-JP **Accent** | **全公開モデル中1位**（目標 ≤ 8%） | 主戦場 |
| カナCER ↓ | LilyBench-JP Basic | ベースモデルの50%以下 | |

| SIM・UTMOSv2 | Zero-shot / Basic | ベースから劣化させない（Δ ≥ −0.01） | 総合品質は維持 |
| 遅延（ローカル） | 5070 Ti | 初回音声 ≤ 400ms | 実用に耐えること |

## 3. ベースモデルの選定

| 候補 | ライセンス | 日本語 | 16GB で学習できるか | 判断 |
|---|---|---|---|---|
| **Qwen3-TTS-12Hz-1.7B-Base** | Apache-2.0（公式モデルカード） | CER 3.82（報告値） | LoRA なら可 | **第一候補** |
| Qwen3-TTS-12Hz-0.6B-Base | Apache-2.0 | CER 6.40（報告値） | 全パラメータ学習も可 | アブレーション用・保険 |
| Fun-CosyVoice3-0.5B | Apache-2.0（二次情報、要確認） | 対応 | 全パラメータ学習も可 | 第二候補（P0 で比較） |
| Irodori-TTS（500M） | MIT | 日本語特化 | 可 | NAR なので PK 入力の追加は別設計になる。比較対象 |
| Sarashina2.2-TTS | 非商用との情報あり | 日本語特化 | — | 比較対象のみ |

- 12Hz のトークナイザは1秒あたりのフレーム数が少ないので、**同じ音声時間あたりの学習コストが安い**。16GB 環境には大きな利点。
- **P0 で LilyBench-JP を使って全候補を実測してから確定する**。読みとアクセントの誤りがどこに多いかもここで分かる。

## 4. システム構成

```
入力テキスト（ルビ {今日|こんにち} / アクセント指定 {橋|ハ[シ} 可）
   │
   ▼
[正規化]（ルールは最小限。数詞の読み分けなどは Yomi に任せる）
   │
   ▼
[Yomi: 読み・アクセント推定器]  日本語LLM 〜1.7B + LoRA          ← RTX 3050 でも動く
   │  出力: PK列  例) ^ キ[ョ]ーワ # ヨ]イ # テ]ンキデスネ $
   │  ルビやアクセント指定の部分は制約付きデコードで固定する
   ▼
[Lily: 音響モデル]  Qwen3-TTS-12Hz-1.7B-Base + LoRA                  ← RTX 5070 Ti
   │  入力: 「本文 <sep> PK列」＋ 参照音声（3〜10s）＋ 任意のスタイル指示
   ▼
波形（サンプリングレートはベースモデルのまま） → [透かし]
```

### 4.1 2モデルに分ける理由（フルスケール版の「1モデルで CoT」との違い）

- Yomi は**テキストだけのデータで何百万文でも学習できる**。音声モデルを回さないので、5070 Ti で1日あれば学習が終わる。
- Lily 側は「PK に従って読む」ことだけ学べばよく、**少ない音声データ（1〜3k時間）で足りる**。
- ベース TTS に PK 生成まで学ばせると、元の能力が壊れる危険が大きい。分ければ、その危険を Yomi 側に閉じ込められる。
- 推論時は Yomi を RTX 3050 に載せ、2枚の GPU を活かせる。

### 4.2 PK列の仕様

フルスケール版 §4.1 と同じ（ESPnet / pyopenjtalk の prosody 記号と互換）。
`^ $ ?`（文頭・文末・疑問）、`#`（アクセント句の境界）、`[`（ピッチ上昇）、`]`（アクセント核）、`_`（ポーズ）。
**記号はすべて ASCII またはカナなので、Qwen 系のトークナイザに語彙を追加しなくても通る**。

### 4.3 Lily の入力形式（学習時のドロップアウト）

| 割合 | 入力 | 目的 |
|---|---|---|
| 60% | 本文 `<sep>` PK | 基本形。本文から意味を、PK から読みとアクセントを取る |
| 25% | PK のみ | PK への忠実さを強める（ユーザーが上書きしたときに効く） |
| 15% | 本文のみ | ベースの能力を保ち、Yomi が使えないときの退避路にする |

## 5. データ（目標 1〜3k時間）

### 5.1 データ源

| データ | 規模の目安 | 用途 | 注意 |
|---|---|---|---|
| JSUT / JVS / JVNV / つくよみちゃん / ITA コーパス朗読 | ~100h | 高品質。**アクセントラベラの教師**（jsut-label 等の人手ラベル） | 各ライセンスを確認 |
| Common Voice ja | ~100h〜 | 話者の多様性 | CC0 |
| ReazonSpeech（高品質な部分だけ抽出） | ~1〜2k h | 主データ | 30条の4 前提。配布・商用は要確認 |
| Emilia / Emilia-YODAS の ja | ~0.5〜1k h | 自然な発話 | NC の可能性あり、要確認 |
| 自前録音（自分・協力者） | 数時間〜 | SFT・デモ話者 | 同意書を取る |
| **テキストのみ**（Wikipedia・青空文庫・ニュース等） | 数百万文 | Yomi の学習 | |

- 目安として、**保存領域は 1〜2TB の SSD**（16kHz〜24kHz の FLAC で保存し、処理後はトークンだけ残す）、RAM は 32〜64GB。
- 書き起こしは**既存のものを再利用**し、全量を ASR にかけ直すことはしない。品質フィルタで外れたものだけ ASR で再確認する。

### 5.2 前処理（RTX 3050 で常時バックグラウンド実行）

```
音声 → 長さ・音量の正規化 → 品質フィルタ（UTMOSv2 / DNSMOS / SNR）上位を残す
     → ASR の一致確認（kotoba-whisper。既存書き起こしと CER < 5%）
     → ★ PKラベラ（§5.3）で実際の読みとアクセントを付ける
     → Qwen3-TTS トークナイザで音声トークン化して保存（ここで生音声は不要になる）
```

### 5.3 ★ PKラベラ（音声から読みとアクセントを取る）

この計画の品質の核心。どれも小さく、すぐ学習できる。

| 部品 | 中身 | 学習コスト（5070 Ti） |
|---|---|---|
| カナ音素認識器 | rinna/japanese-hubert-base（95M）を CTC でカナ出力に微調整。教師は JSUT / JVS の読みと、OpenJTalk の読みのうち高信頼なもの | ~10時間 |
| 辞書で制約したデコード | pyopenjtalk(-plus) / UniDic / marine の N-best 読み候補を、認識器のスコアで選ぶ | 学習なし |
| アクセント推定器 | 強制アライメント → RMVPE で F0 → モーラごとの高低 → 小さな分類器（辞書の事前分布と音響を統合）。教師は人手アクセントラベル | ~1時間 |
| 信頼度 | 低信頼の発話は「本文のみ」入力の学習に回す | — |

### 5.4 Yomi 用のテキストデータ（GPU をほとんど使わない）

1. **音声由来の (本文, PK)**: §5.3 の出力。最も信頼でき、数十万〜百万文規模になる。
2. **辞書アンサンブル**: 大量のテキストに pyopenjtalk / marine で PK を付ける。ただし、同形異音語・数詞・固有名詞を含む文には**信頼度が低い印を付け、重みを下げる**。
3. **難例合成**: 同形異音語の辞書（~3,000語）、数詞×助数詞、日付・時刻・金額・単位、駅名・地名・人名の辞書から、テンプレートとローカル LLM（例: 14B 級を 4bit 量子化して 5070 Ti で夜間に回す）で例文を作る。正解の読みは辞書と規則で付け、**人手で抜き取り検査する**。
4. **評価との汚染防止**: Yomi-Hard の文や語の組み合わせは学習データから除外する。

## 6. 学習計画と VRAM 予算

### 6.1 Yomi（テキスト → PK）

- ベース候補は LLM-jp-3 1.8B（Apache-2.0）/ Sarashina2.2-1B / Qwen3-1.7B。テキストだけで安く学習できるので**3つとも試して決める**。
- LoRA（r=64、全 linear 層）、bf16、系列長 256、約3億トークン → **5070 Ti で約1日**。
- その後、RL で読みを詰める。正解 PK との一致（読み・核・句境界の重み付き）を報酬に GRPO を回す。テキストだけなので安い。
- 必要なら 0.6B に蒸留し、3050 で高速に推論できるようにする。

### 6.2 Lily（PK → 音声）

| 項目 | 設定 |
|---|---|
| ベース | Qwen3-TTS-12Hz-1.7B-Base |
| 方式 | LoRA（r=64〜128、attention と MLP）。コーデック・デコーダ側は凍結 |
| 精度 | bf16（Blackwell の FP8 学習は任意。ツールの対応状況を見て判断） |
| メモリ節約 | gradient checkpointing、トークン数でのバッチ構成（長さソート）、8bit AdamW |
| データ | 1〜3k h × 12.5Hz ≈ 4,500万〜1.35億フレーム（エポックあたり） |
| 計算量 | 2k h・3エポックで ~2e18 FLOPs → **約1〜2日** |
| VRAM 見積り | 重み 3.4GB + LoRA と最適化状態 <1GB + 活性値 → 12〜14GB に収まる見込み |

### 6.3 選好学習（DPO → 余力があれば GRPO）

1. **RTX 3050** でプロンプト5,000件 × 4サンプルを生成する（並行して実行）。
2. 自動で採点する: `R_read`（カナ音素認識器による PK との一致）、`R_acc`（アクセント推定器）、`R_sim`、`R_mos`（UTMOSv2）。
3. 勝ち負けのペアを作り、5070 Ti で DPO-LoRA を数時間回す。
4. **報酬ハッキング対策**: 評価には報酬とは別の ASR（Whisper-large-v3 等）を使う。人手でも抜き取り試聴する。

### 6.4 GPU 時間の合計

| 作業 | GPU | 時間 |
|---|---|---|
| ベースラインの評価（P0） | 3050 + 5070 Ti | 2〜3日 |
| PKラベラの学習 | 5070 Ti | ~半日 |
| 前処理・ラベル付け・トークン化（2〜3k h） | 3050（常時） | 4〜7日（並行） |
| Yomi の LoRA 学習と RL（候補3つ） | 5070 Ti | 3〜4日 |
| Lily の LoRA 学習（本番） | 5070 Ti | 2〜3日 |
| アブレーション（0.6B・300h の小規模で6本） | 5070 Ti | ~1週 |
| DPO（生成と学習） | 両方 | 2〜3日 |
| **合計** | | **GPU 時間で約3〜5週** |

長時間の学習に備えて、チェックポイントからの再開を必須にする（停電・ドライバ更新への対策）。

## 7. 評価: LilyBench-JP（個人規模版）

| サブセット | 規模 | 作り方 | 指標 |
|---|---|---|---|
| Basic | 500文 | 多ジャンルから抽出 | CER、カナCER、UTMOSv2 |
| **Yomi-Hard** | 500文 | 同形異音語・数詞・固有名詞・英字混じりを**人手で作成し、読みを確定** | 文単位の読み完全一致率（カナ音素認識器 + 人手確認） |
| **Accent** | 200文 | **人手でアクセントを付ける**（NHK アクセント辞典等を参照） | アクセント句誤り率（自動）＋人手 A/B |
| Zero-shot | 話者50 × 4文 | Common Voice / JVS の評価用話者 | SIM、CER |
| 公開互換 | — | 公開ベンチの ja 部分 | CER（他社の報告値と比較） |

- 比較対象: Qwen3-TTS（ベース）/ CosyVoice3 / Irodori-TTS / Sarashina2.2-TTS / Style-BERT-VITS2 JP-Extra / VoxCPM2 / 可能なら商用 API。
- 評価用モデル（Whisper-large-v3、UTMOSv2、WavLM-SV）は **3050 に常駐**させる。
- 主観評価を SOTA の主張に使うなら、クラウドソーシングで**ネイティブ20名以上**を集める必要がある。これは費用が発生するので、v1 では自動指標と少人数の A/B で済ませ、公開前に実施するかどうか決める。

## 9. 推論

- **Yomi は RTX 3050**（bf16 で約3.5GB、4bit なら約1.2GB）、**Lily は RTX 5070 Ti**。
- ストリーミング: 文や節の単位で `Yomi → Lily` を流す。Yomi は次の文を先読みして処理する。
- 1GPU 構成（5070 Ti のみ）でも、2モデル合わせて VRAM 8GB 前後で動く見込み。
- 出力には透かし（AudioSeal 等）を入れる。

---

## 10. ソフトウェア環境の注意（Blackwell / sm_120）

- PyTorch は **CUDA 12.8 以降のビルド**が必要（5070 Ti は sm_120）。古い wheel は動かない。
- FlashAttention や bitsandbytes などの拡張は、**sm_120 対応版かどうかを最初に確認**する。動かなければ PyTorch 標準の SDPA と通常の AdamW に切り替える。
- 2枚は**別プロセス・別ジョブ**で使う（`CUDA_VISIBLE_DEVICES` で分ける）。DDP は使わない。

## 12. リスクと対策

| リスク | 対策 |
|---|---|
| LoRA では PK に十分従わない | rank を上げる → 0.6B を全パラメータで学習する → CosyVoice3-0.5B を全パラメータで学習する、の順で退避する |
| アクセントラベルの質が低い | 人手ラベル付きの高品質データで重みを上げる。低信頼のデータは「本文のみ」の学習に回す |
| データのライセンス | `data/LICENSES.md` に台帳を作り、公開する重みは許諾が明確なデータだけで学習する系統に分ける |
| 人手評価が足りない | 自動指標を複数の ASR で測る。公開前にクラウドソーシングをするか判断する |
| 16GB の VRAM 不足 | 系列長の上限を設定、オプティマイザ状態を CPU に退避、0.6B に切り替える |
| 声のなりすまし | 透かしの必須化、利用規約、実在人物の既定話者は作らない |
