# LilyTTS-JP 設計書 v0.1

> 目標: **日本語で「読み」「アクセント」「自然性」「話者再現」の全指標で公開SOTAを取る**ゼロショットTTS。
> 最終更新: 2026-11-22

## 0. TL;DR

| 項目 | 方針 |
|---|---|
| 全体構成 | **AR言語モデル（日本語LLM初期化）→ 意味トークン → チャンク因果Flow Matching → 48kHz 連続潜在 → VAEデコーダ** の2段ハイブリッド |

| データ | フィルタ後 **日本語 約10万時間**＋英中 約3万時間。ラベルは**音声から取った実際の読みとアクセント**（G2Pの推定ではない） |
| 事後学習 | SFT → **多報酬GRPO/DPO**（カナCER・アクセント正解率・話者類似度・MOS予測）。PK生成部はテキストだけのRLで安く鍛える |
| 評価 | 独自ベンチ **LilyBench-JP**（Yomi-Hard / Accent / Zero-shot / Expressive / Long-form）に加え、公開ベンチ（CV3-Eval ja 等）でも比較できるようにする |
| 規模 | LM 1.7B + FM 0.3B + トークナイザ 0.6B。総計算量の見積り 8k〜15k H100時間（アブレーション込み） |

## 1. 「SOTA」の定義と目標値

SOTAを主張するには、**比較できる公開指標**と、**日本語固有の弱点を測る独自指標**の両方で勝つ必要がある。

### 1.1 現状の参照値（2026年11月時点の調査、要再確認）

- 多言語ゼロショットTTSの日本語CERは、上位勢でおおむね **3.5前後**（MiniMax 3.52、Qwen3-TTS 12Hz-1.7B 3.82、Confucius4-TTS 4.14、ElevenLabs 10.65 など。比較表によって評価セットが違う点に注意）。
- 日本語特化のオープンモデルとして **Sarashina2.2-TTS**（約0.8B、漢字の多義読みに特化、非商用ライセンスとの情報あり）、**Irodori-TTS**（500M Flow Matching、MIT）がある。
- **VoxCPM2** はモデルカードで「漢字の読みが弱いので先にひらがなへ変換を」と明記している → **漢字の読みは業界全体の未解決課題**。
- アクセントについては、**発話単位のMOS予測モデルはアクセントの誤りに鈍い**という報告がある（PASQA）。つまり既存のSOTA主張はアクセントの質をほぼ測っていない。ここが狙い目。

### 1.2 目標値（v1リリース時）

| 指標 | 評価セット | 目標 | 備考 |
|---|---|---|---|
| CER ↓ | CV3-Eval ja / 公開多言語ベンチ ja | **≤ 2.5** | 上位勢 ~3.5 を明確に下回る |
| カナCER ↓ | LilyBench-JP Basic | ≤ 1.5 | 読みを直接測る（§10.2） |
| 読み正解率 ↑ | LilyBench-JP **Yomi-Hard** | **≥ 97%**（文単位完全一致） | 同形異音語・数詞・固有名詞 |
| アクセント句誤り率 ↓ | LilyBench-JP **Accent** | **≤ 5%** | 人手アクセントラベル付き |
| 話者類似度 SIM ↑ | Zero-shot set | ≥ 0.75 | WavLM-large SV |
| UTMOSv2 ↑ | Basic | 自然音声以上 | |
| CMOS | 人手評価 | 最良の商用モデルに対して **≥ 0** | ネイティブ20名以上 |
| 初回パケット遅延 ↓ | ストリーミング | ≤ 150 ms | 1×H100, batch=1 |

## 2. 日本語TTSの難所

既存モデルの失敗は、ほぼ次の4つに分類できる。設計はこの順に対策する。

1. **漢字の読み（同形異音語）**
   今日（きょう／こんにち）、上手（じょうず／うわて／かみて）、人気（にんき／ひとけ）、方（かた／ほう）、日本橋（にほんばし／にっぽんばし）、生物（せいぶつ／なまもの）。
   文脈を見ないと決まらない。辞書ベースのG2P（OpenJTalk等）は文脈理解が浅い。
2. **数詞・助数詞・記号**
   3本（さんぼん）、1分（いっぷん）、6回（ろっかい）、20日（はつか）、2026/11/22、¥1,980、3:00、10km、No.1、URL、絵文字、顔文字。
3. **ピッチアクセント**
   語彙ごとのアクセント核（箸／橋／端）、**アクセント結合**（複合語・助詞付加で核が移る）、アクセント句の区切り、疑問の上昇調。**読みが正しくてもアクセントが崩れると「外国人っぽい」「機械っぽい」と即座に気づかれる**。
4. **音声現象**
   母音の無声化（す、し）、長音・促音・撥音の拍長、連濁、鼻濁音、英語由来語のカタカナ発音、言いよどみやフィラー（えーと、あのー）。

→ 1・2は**テキスト側の知識**、3は**テキスト知識と音響を両方つなぐ情報**、4は**音響モデル側**の問題。
→ そこで「テキスト→PK列（読み＋アクセント）」と「PK列→音声」を**一つのLMの中で明示的に分けつつ、まとめて学習する**（§4）。

                                                ▼  48kHz 連続潜在 (50Hz, 64ch)                  │

### 3.1 この構成を選ぶ理由

| 選択肢 | 利点 | 欠点 | 判断 |
|---|---|---|---|
| VITS系（Style-BERT-VITS2等） | 軽い・アクセント制御が明示的 | ゼロショット・大規模化に弱い | ベースラインとして使う |
| NAR単段（F5-TTS / Irodori型） | シンプル・高品質 | 長さ予測と読みの制御が弱く、テキスト知識を入れにくい | アブレーションで比較 |
| ARコーデックLM単段（Llasa型） | 単純・スケールしやすい | 細かい音質で劣り、遅い | 不採用 |
| **AR LM + FM（CosyVoice型）** | LLMの言語知識・韻律の多様性・ストリーミング・高音質を両立 | 構成が複雑 | **採用** |

決め手は、**読みとアクセントはテキスト知識の問題なので、日本語LLMの事前知識を直接使えるAR LMに担当させるべき**という点。

## 4. テキストフロントエンドと「読み思考（Reading-CoT）」

### 4.1 PK列（Prosodic Kana）の仕様

カナ（モーラ単位）とアクセント記号を並べた列。ESPnet / pyopenjtalk の prosody 記号と互換にする。

| 記号 | 意味 |
|---|---|
| `^` / `$` / `?` | 文頭 / 平叙文末 / 疑問文末 |
| `#` | アクセント句の境界 |
| `[` | ピッチの上昇 |
| `]` | アクセント核（下降） |
| `_` | ポーズ |
| `ー` `ッ` `ン` | 長音・促音・撥音（1モーラとして数える） |
| `ˇ`（任意） | 無声化母音 |

例: `今日は良い天気ですね。` → `^ キ[ョ]ーワ # ヨ]イ # テ]ンキデスネ $`

語彙: カナモーラ 約150 ＋ 記号 約10 ＋ 英語音素（ARPAbet 39）＋ 中国語拼音（声調付き）を LLM の語彙に追加する。

### 4.2 LMの入出力列

```
<|sys|>  スタイル指示（例: 落ち着いた低めの声で、ゆっくり）
<|ptxt|> 参照テキスト      <|ppk|> 参照PK      <|pspk|> 参照音声トークン
<|text|> 合成テキスト
<|pk|>   合成PK            ← LMが生成する（読み思考） / ユーザー指定時は強制
<|spk|>  合成音声トークン   ← LMが生成する
```

- **学習時のドロップアウト**: 70% は PK を使う。15% は PK を飛ばしてテキストから音声を直接作る（PK なしでも動くようにするため）。15% はテキストを部分的にマスクして PK から音声を作る（ユーザーが PK を指定したとき、それに忠実に従わせるため）。
- **部分的な上書き**: ルビ `{日本橋|ニッポンバシ}` やアクセント指定 `{橋|ハ[シ}` は、その範囲だけ PK のデコードを強制し、残りは LM に任せる（制約付きデコード）。
- **ストリーミング**: 文（またはアクセント句のまとまり）単位で `text→PK→speech` を交互に並べる（§9）。PK の生成はテキスト長に比例する短い列なので、遅延への影響は小さい。

### 4.3 Reading-CoTの利点

1. **テキストだけのデータで読みを学習できる**: (テキスト, PK) の組は音声なしで何億文でも作れる（§6.4）。読みの誤りの多くはここで潰せる。
2. **誤りの切り分けができる**: 読みの誤りなら PK 段、発音や音質の誤りなら音声段、と原因がはっきりする。報酬も段ごとに設計できる（§8）。
3. **ユーザーが修正できる**: 業務用途（ナレーション、ゲーム、教材）では読みとアクセントを直せることが必須条件。
4. **解釈しやすい**: どう読むつもりかを、音声にする前にログで確認できる。

### 4.4 正規化

- Unicode: NFKC を基本とし、全角記号・波ダッシュ・絵文字・顔文字は例外表で扱う。
- **数詞・日付・単位・通貨・時刻・URL・型番は、ルールで直さず LM（PK段）に任せる**のが基本方針。ルールは読みが一意に決まる正規化（桁区切りの除去など）だけにとどめる。数詞の助数詞変化や「20日＝はつか」は PK 段の学習データ（§6.4）で教える。
- 英字略語・英単語: そのまま入力する。PK 段がカタカナ読み（例: `AI → エーアイ`）または英語音素を選ぶ。

## 5. 音声トークナイザ（意味トークン）

### 5.1 構成

- **エンコーダ**: w2v-BERT 2.0 か Whisper-large-v3 のエンコーダで初期化し、約600Mパラメータ。
- **量子化**: FSQ の単一コードブック（|V| = 6561 = 3^8）、**25Hz**。
- **学習目標**（すべて同時に学習する）:
  1. **PK列を教師とした ASR**（CTC と、注意機構付きの小さなデコーダ）。日本語の音声についてはテキストではなくカナとアクセント記号を予測させる。こうするとトークンに**読みとアクセント核の情報が残る**。ここが CosyVoice の S3 トークナイザ（テキストASRのみで学習）との違い。
  2. **フレーム単位の F0 回帰**（発話ごとに正規化した log-F0 と有声/無声の判定）。イントネーションをトークンに残すため。
  3. **話者の敵対的損失**（勾配反転）。話者性はトークンから追い出し、FM 側のプロンプトに担当させる。
- 英語・中国語は通常のテキスト ASR を教師にする。

### 5.2 検証項目

- トークン→再合成した音声の**カナCER**、**アクセント句誤り率**、F0 相関。
- トークン列だけからアクセント核を当てる線形プローブの精度（目標 ≥ 95%）。

## 6. データ

### 6.1 規模とデータ源

| 区分 | 目標時間（フィルタ後） | 候補データ源 | 用途 |
|---|---|---|---|
| 日本語・実環境 | ~90k h | ReazonSpeech、YODAS(ja)、Emilia / Emilia-YODAS の ja、ポッドキャスト、オーディオブック | 事前学習 |
| 日本語・高品質 | 300〜800 h | **権利処理済みの自前スタジオ収録**（声優・ナレーターと明示的に契約）、JSUT、JVS、JVNV、つくよみちゃんコーパス等 | SFT・音質 |
| 日本語・会話 | ~5k h | CSJ（有償）、会話系ポッドキャスト | フィラーや自然なリズム |
| 英語・中国語 | ~30k h | Emilia (en/zh)、LibriHeavy 等 | コードスイッチ・外来語 |
| テキストのみ (Text, PK) | **数億文** | 日本語Web・書籍・Wikipedia・ニュースのテキスト | PK段の学習 |

> ⚠ **ライセンス**: 各データの利用規約を一件ずつ確認する（§13）。ReazonSpeech のような「著作権法30条の4」を前提としたデータは、**学習には使えても、配布や商用利用の可否は別問題**。アニメやゲームの音声を抜き出したデータセットは、声優の権利の点で使わない。

### 6.2 前処理パイプライン（Emilia型を拡張）

```
生音声
 → 音源分離（BGM除去: MDX/Demucs系）
 → VAD・分割（3–30s）
 → 話者ダイアライゼーション（pyannote系）→ 単一話者区間だけ残す
 → 品質フィルタ（DNSMOS / UTMOSv2 / SNR / クリッピング / 帯域推定。48kHz用には実効帯域 ≥ 16kHz）
 → 複数ASRで書き起こし（Whisper-large-v3、kotoba-whisper、ReazonSpeech系）
     → ASR同士の一致度（CER < 5%）で採否を決め、句読点を復元する
 → ★ 読み・アクセントの自動ラベリング（§6.3）
 → 発話スタイルタグ付け（感情・話速・ささやき・笑い等。音声キャプションモデルとLLMで作る）
 → 重複除去（音響指紋）・評価セットとの汚染チェック
```

### 6.3 ★ 音声から取る読み・アクセントラベル（PKラベラ）

**G2Pの推定ではなく、実際にどう読まれたか**を教師にすることが品質の核心になる。

1. **カナ音素認識器**: w2v-BERT 2.0 を CTC でカナ出力に微調整する。教師は JSUT / JVS / CSJ の読みラベルと、OpenJTalk ラベルのうち ASR と一致した高信頼部分。
2. **辞書で制約したデコード**: 書き起こしテキストから OpenJTalk / UniDic / marine の **N-best 読み候補**（アクセント付き）を作り、音素認識器のスコアで最良の候補を選ぶ。候補外の読みは認識器の結果を採用する（Transcript-Prompted Whisper + 辞書強化デコードの考え方を応用）。
3. **アクセント推定**: 強制アライメントでモーラ境界を出し、F0（RMVPE / FCPE）からモーラごとの高低を出す。そのうえで分類器がアクセント核とアクセント句境界を決める。分類器は辞書の事前分布と音響の証拠を組み合わせ、JSUT / JVS 等の人手アクセントラベルで学習する。
4. **信頼度**: 発話ごとに信頼度を記録する。低信頼の発話は PK なしの学習（§4.2 の15%枠）に回す。

### 6.4 テキストのみの (Text, PK) データ

- **教師**: §6.3 のラベラで作った音声由来の (Text, PK) に加え、辞書 / OpenJTalk / marine の候補を LLM（日本語に強い大型モデル）に文脈から選ばせて作る。人手で作る難例セットも加える。
- **難例の合成**（Sarashina2.2-TTS の「targeted data synthesis」と同じ方向）:
  - 同形異音語の辞書（約3,000語）から LLM で文脈の異なる例文を大量に生成し、正解の読みを付ける。
  - 数詞×助数詞の全組み合わせ、日付・時刻・金額・単位・型番のテンプレート文。
  - 固有名詞（地名・駅名・人名）の読み辞書から作る文。
- 合成した難例は**音声も作る**: 現行モデルに正解PKを強制してTTSし、カナASRで検証して合格したものだけを音声段の学習に混ぜる（自己蒸留ループ）。

## 7. モデル詳細

### 7.1 AR LM

| 項目 | 値 |
|---|---|
| 初期化 | 日本語に強い約1.7Bの LLM。候補は Qwen3-1.7B、LLM-jp-3 1.8B、Sarashina2.2-1B。**ライセンス、日本語トークナイザの効率、日本語の読み理解ベンチ**で選ぶ |
| 追加語彙 | PKトークン 約250 + 意味トークン 6561 + 制御トークン |
| 文脈長 | 8k（テキスト + PK + 参照3〜10s + 合成 最大60s） |
| 損失 | PK と音声トークンの CE。重みは PK 1.0 / 音声 1.0。テキストのみのバッチでは PK の CE だけ |
| 話者埋め込み | 使わない（プロンプトの文脈内学習に任せる） |
| 制御 | `<|sys|>` に自然言語のスタイル指示を書く。`[笑]` `[息]` `[ため息]` `[咳払い]` などの非言語タグも使える |

### 7.2 Flow-Matching デコーダ

- **DiT 約0.3B**。条件は「意味トークン（25Hz→50Hzに上げる）」と「参照音声の VAE 潜在」と「F0 の任意ヒント」。
- **チャンク因果マスク**（CosyVoice 2 型）で、オフライン合成とストリーミングを同じ重みで扱う。
- サンプリング: 学習後に **shortcut / consistency 蒸留**で 2〜4 ステップにする。CFG は話者と内容で別々の重み。

### 7.3 音響潜在 VAE

- 48kHz 波形 ↔ 50Hz × 64ch の連続潜在。GAN 損失 + 多重解像度 STFT 損失で学習。
- **代替案**: 24kHz メル + BigVGAN-v2 型ボコーダ。VAE で音質が出ないときの保険として並行して用意する。

## 8. 学習レシピ

| 段階 | 内容 | データ |
|---|---|---|
| S0 | VAE と意味トークナイザを学習 | 全音声 |
| S1 | **LM 事前学習**: テキストのみ (Text→PK) と音声 (Text→PK→Speech) を混ぜる（トークン比でテキストのみ 30%）。英中も混ぜる | 全データ |
| S2 | FM 事前学習 | 全音声 |
| S3 | **SFT**: 高品質セット・スタイル指示付きデータ・難例合成データ | 高品質 + 難例 |
| S4 | **選好学習 / RL**（§8.1） | 生成サンプル |
| S5 | FM の少ステップ蒸留とストリーミングの微調整 | 高品質 |

### 8.1 事後学習（多報酬RL）

**PK段（テキストのみなので安い）**
- 報酬: 人手・高信頼の正解 PK との一致（読み・アクセント核・句境界ごとに重み付け）。
- 手法: GRPO。1入力あたり 8〜16 サンプル。

**音声段**
- 報酬:
  - `R_read`: 生成音声をカナASRにかけ、指定PKとのカナCERを計算する。読みの忠実さを測る。
  - `R_acc`: 生成音声のアクセント推定（§6.3 の推定器）が指定PKのアクセントと一致するか。加えて PASQA 型のアクセント品質モデル。
  - `R_sim`: 参照音声との話者類似度。
  - `R_mos`: UTMOSv2 等の MOS 予測値。
  - `R_len`: 異常な長さ・無音・繰り返しへのペナルティ。
- 手法: DPO（勝ち負けペア）から始め、安定したら GRPO に移る。報酬ハッキング対策として、**学習に使うASRとアクセント推定器を、評価に使うものとは別モデルにする**。KL 正則化もかける。

---

## 9. 推論とストリーミング

- テキストを文単位に分割し、`[text_i][PK_i][speech_i]` を順に生成する。テキストを先読みして、文をまたぐ文脈を確保する。
- LM: vLLM / TensorRT-LLM の KV キャッシュと連続バッチングで動かす。
- FM: チャンク長 0.5s、2〜4 ステップ。VAE デコーダはストリーミング対応の因果畳み込み。
- 目標: 初回パケット ≤ 150ms、RTF ≤ 0.1（1×H100）。民生GPU（RTX 4090）でも RTF ≤ 0.3。
- 出力: 48kHz、AudioSeal 型の**透かしを必ず埋め込む**。

## 10. 評価: LilyBench-JP

### 10.1 構成

| サブセット | 規模 | 内容 | 主指標 |
|---|---|---|---|
| Basic | 1,000文 | ニュース・会話・小説・技術文 | CER, カナCER, UTMOSv2 |
| **Yomi-Hard** | 1,000文 | 同形異音語・数詞と助数詞・固有名詞・地名・英字混じり・記号 | 読み正解率（文単位完全一致） |
| **Accent** | 500文 | 人手アクセントラベル付き（アクセント結合・複合語・疑問調を含む） | アクセント句誤り率、アクセントMOS |
| Zero-shot | 話者200 × 5文 | 年齢・性別・方言・録音環境を幅広く | SIM, CER |
| Expressive | 500文 | 感情（JVNV系）・ささやき・叫び・スタイル指示 | 指示追従の判定・感情認識の一致率 |
| Long-form | 20本 × 5分 | オーディオブック・ニュース原稿 | 挿入・脱落率、話者のドリフト |
| 公開互換 | — | CV3-Eval ja など公開ベンチの日本語部分 | CER, SIM（他社表と比較するため） |

### 10.2 指標の注意点

- **CER**: 漢字の表記ゆれ（「出来る」と「できる」など）を避けるため、ASR結果と正解を**両方ともカナに変換して比べる「カナCER」も併記する**。カナCERは読みを直接測る指標になる。
- **ASRは2種類以上**（Whisper-large-v3、kotoba-whisper など）で測り、学習時の報酬に使ったモデルは評価から外す。
- **アクセント**: 自動の推定器と PASQA 型モデルに加えて、**ネイティブ評定者がアクセントの自然さを A/B 比較する**。
- **主観評価**: MOS / SMOS / CMOS を、ネイティブ20名以上 × 各条件30文以上で行い、95%信頼区間を報告する。

### 10.3 比較対象

Style-BERT-VITS2 JP-Extra / Irodori-TTS / Sarashina2.2-TTS / CosyVoice 3 / Qwen3-TTS / IndexTTS-2.5 / VoxCPM2 / Fish Audio 系 / 商用（ElevenLabs、MiniMax など）。
**P0 の段階で全モデルを LilyBench-JP で測り、本当の SOTA の値をこちらで確定させる。**

## 13. リスク・法務・安全

| リスク | 対策 |
|---|---|
| データのライセンス | データ源ごとに台帳（`data/LICENSES.md`）を作り、利用範囲を研究 / 商用 / 配布に分ける。商用モデルは許諾済みのデータだけで学習する系統を別に用意する |
| 声の権利（声優・パブリシティ） | 特定の実在人物の声を模倣した既定話者は作らない。自前収録では同意書に「合成モデルの学習・公開」を明記する |
| 声のなりすまし | 透かしの必須化、検出器の公開、利用規約による本人同意の義務化、著名人の声を照合する拒否リスト |
| 報酬ハッキング | 学習用と評価用の ASR・推定器を分ける。人手評価を定期的に入れる |
| 評価セットの汚染 | 評価文と学習データの n-gram 重複・音響指紋を照合する |
| 競合が先に進む | P0 で現在値を確定させ、その後も四半期ごとに再評価する |

## 14. リポジトリ構成（予定）

```
LilyTTS-JP/
├── docs/                 設計書・評価仕様・データ台帳
├── lilytts/
│   ├── text/             正規化・マークアップ解析・PK仕様・トークナイザ
│   ├── labeler/          カナ音素認識・辞書制約デコード・アクセント推定（PKラベラ）
│   ├── tokenizer/        意味トークナイザ (FSQ)
│   ├── vae/              48kHz 音響潜在 VAE
│   ├── lm/               AR LM（Reading-CoT）
│   ├── fm/               Flow-Matching DiT
│   ├── rl/               報酬モデル・GRPO/DPO
│   └── infer/            ストリーミング推論・サーバ
├── data_pipeline/        分離・VAD・ダイアライゼーション・ASR・フィルタ
├── bench/                LilyBench-JP（データ定義・評価スクリプト・競合モデルのラッパ）
├── configs/
└── scripts/
```

**最初の実装順**: `bench/`（P0）→ `lilytts/text/`（PK仕様）→ `lilytts/labeler/` → `data_pipeline/`。
評価基盤を最初に作るのは、SOTAかどうかを判定できない状態で学習を始めないため。
